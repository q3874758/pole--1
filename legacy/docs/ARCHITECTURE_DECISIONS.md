# 架构决策记录 (ADR)

## ADR-001: 选择 Go + Rust 混合架构

**日期**: 2026-01-15

**状态**: 已接受

### 背景

PoLE 需要一个高性能、可维护的技术栈来实现区块链核心功能和游戏数据采集。

### 决策

采用 Go + Rust 混合架构:
- **Go**: 区块链核心、RPC 服务器、网络层
- **Rust**: 性能关键模块（类型系统、数据采集、GVS 计算）

### 理由

**Go 的优势**:
- 优秀的并发支持（goroutines）
- 丰富的区块链生态（Cosmos SDK、Tendermint）
- 快速开发和部署
- 良好的网络编程支持

**Rust 的优势**:
- 内存安全保证
- 零成本抽象
- 高性能计算
- 适合系统级编程

### 后果

**正面**:
- 充分利用两种语言的优势
- 性能关键路径使用 Rust 优化
- 业务逻辑使用 Go 快速迭代

**负面**:
- 需要维护两套工具链
- FFI 调用有一定开销
- 团队需要掌握两种语言

## ADR-002: 使用 Cosmos SDK 作为区块链框架

**日期**: 2026-01-20

**状态**: 已接受

### 背景

需要选择一个成熟的区块链开发框架来加速开发。

### 决策

使用 Cosmos SDK 作为基础框架。

### 理由

1. **模块化设计**: 可以自定义共识机制
2. **成熟稳定**: 经过多个项目验证
3. **IBC 支持**: 未来可以跨链互操作
4. **开源免费**: 无商业授权费用
5. **活跃社区**: 丰富的文档和支持

### 替代方案

- **Substrate**: Rust 生态，但学习曲线陡峭
- **Tendermint**: 需要更多底层开发
- **自研**: 开发周期长，风险高

### 后果

**正面**:
- 快速启动开发
- 利用现有生态工具
- 降低开发风险

**负面**:
- 依赖外部框架
- 需要适应 Cosmos 的设计模式

## ADR-003: EVM 兼容性设计

**日期**: 2026-01-25

**状态**: 已接受

### 背景

需要决定智能合约层的设计方案。

### 决策

通过 Ethermint 模块实现 EVM 兼容。

### 理由

1. **生态兼容**: 直接使用以太坊工具链
2. **开发者友好**: Solidity 开发者可无缝迁移
3. **成熟工具**: MetaMask、Truffle、Hardhat 等
4. **降低门槛**: 无需学习新的智能合约语言

### 替代方案

- **CosmWasm**: Cosmos 原生，但生态较小
- **自定义 VM**: 开发成本高
- **Move VM**: 新兴技术，生态不成熟

### 后果

**正面**:
- 快速吸引以太坊开发者
- 丰富的 DApp 生态
- 成熟的开发工具

**负面**:
- EVM 性能限制
- Gas 模型复杂性

## ADR-004: 混合共识机制 (PoS + PoLE)

**日期**: 2026-02-01

**状态**: 已接受

### 背景

需要设计一个既安全又能体现游戏参与度的共识机制。

### 决策

采用 PoS + PoLE 混合共识:
- **PoS**: 保证网络安全性
- **PoLE**: 奖励游戏参与度

### 理由

1. **安全性**: PoS 提供经济安全保障
2. **创新性**: PoLE 体现游戏价值
3. **可扩展**: 支持高 TPS
4. **环保**: 相比 PoW 更节能

### 实现细节

- 验证者通过 PoS 选举
- 节点通过 PoLE 获得奖励
- GVS 计算影响奖励分配

### 后果

**正面**:
- 独特的价值主张
- 激励真实游戏参与
- 能源效率高

**负面**:
- 机制复杂性增加
- 需要防止作弊
- 数据源依赖

## ADR-005: 三层游戏分级系统

**日期**: 2026-02-05

**状态**: 已接受

### 背景

不同数据源的可信度不同，需要分级管理。

### 决策

实现三层分级系统:
- **Tier 1**: Steam API 验证（权重 1.0）
- **Tier 2**: 第三方数据（权重 0.45）
- **Tier 3**: 社区验证（权重 0.10）

### 理由

1. **数据可信度**: 反映不同来源的可靠性
2. **激励机制**: 鼓励使用高质量数据
3. **灵活性**: 可以动态调整权重
4. **防作弊**: 降低虚假数据影响

### 后果

**正面**:
- 数据质量保证
- 公平的奖励分配
- 可扩展到更多平台

**负面**:
- 权重设置需要治理
- 可能引起争议

## ADR-006: Gas Credit 零成本机制

**日期**: 2026-02-10

**状态**: 已接受

### 背景

需要实现用户零成本使用网络的目标。

### 决策

实现 Gas Credit 系统:
- 游戏活跃度转换为 Gas Credit
- Credit 可用于支付交易费用
- 真实玩家享受零成本体验

### 理由

1. **用户友好**: 降低使用门槛
2. **激励参与**: 玩游戏即可获得使用权
3. **防止滥用**: 需要真实游戏参与
4. **可持续**: 不影响网络安全

### 实现细节

```
Gas Credit = f(游戏时长, 游戏 Tier, 历史贡献)
```

### 后果

**正面**:
- 真正的零成本体验
- 吸引游戏玩家
- 独特的竞争优势

**负面**:
- 机制复杂性
- 需要防止滥用
- Credit 计算开销

## ADR-007: 使用 libp2p 作为 P2P 网络层

**日期**: 2026-02-15

**状态**: 已接受

### 背景

需要一个成熟的 P2P 网络库。

### 决策

使用 libp2p 实现 P2P 网络。

### 理由

1. **成熟稳定**: 被多个项目使用
2. **功能丰富**: 节点发现、NAT 穿透等
3. **模块化**: 可以自定义协议
4. **跨平台**: 支持多种语言

### 替代方案

- **自研**: 开发成本高
- **Tendermint P2P**: 与 Cosmos 绑定
- **DevP2P**: 以太坊专用

### 后果

**正面**:
- 快速实现网络层
- 利用成熟功能
- 社区支持

**负面**:
- 学习曲线
- 依赖外部库

## ADR-008: 线性释放锁仓机制

**日期**: 2026-02-20

**状态**: 已接受

### 背景

团队和投资人代币需要锁仓释放。

### 决策

实现线性释放机制:
- 1 年锁定期
- 24 个月线性释放
- 链上自动执行

### 理由

1. **保护项目**: 防止早期抛售
2. **公平性**: 透明的释放规则
3. **自动化**: 无需人工干预
4. **可验证**: 链上可查

### 实现细节

```
可领取金额 = 总额 * (当前时间 - 锁定结束) / 释放期
```

### 后果

**正面**:
- 项目稳定性
- 投资者信心
- 透明度高

**负面**:
- 流动性限制
- 实现复杂性

## ADR-009: 紧急暂停机制

**日期**: 2026-02-25

**状态**: 已接受

### 背景

需要应对安全事件的紧急响应机制。

### 决策

实现多级紧急暂停:
- 委员会触发
- 分级暂停（全局/部分）
- 治理恢复

### 理由

1. **安全保障**: 快速响应攻击
2. **灵活性**: 可以部分暂停
3. **去中心化**: 需要治理批准恢复
4. **透明性**: 链上记录

### 暂停级别

- **Full**: 全部功能
- **Transfers**: 仅转账
- **Staking**: 仅质押
- **Governance**: 仅治理

### 后果

**正面**:
- 安全性提升
- 快速响应能力
- 用户资产保护

**负面**:
- 中心化风险
- 可能被滥用
- 用户体验影响

## ADR-010: RESTful HTTP API 设计

**日期**: 2026-03-01

**状态**: 已接受

### 背景

需要设计用户友好的 API 接口。

### 决策

使用 RESTful HTTP API 而非 gRPC。

### 理由

1. **易用性**: 浏览器直接访问
2. **调试方便**: curl、Postman 等工具
3. **文档友好**: OpenAPI/Swagger
4. **广泛支持**: 各语言都有客户端

### 替代方案

- **gRPC**: 性能更好但不够友好
- **GraphQL**: 过于复杂
- **WebSocket**: 适合实时但不适合查询

### 后果

**正面**:
- 开发者体验好
- 易于集成
- 工具支持丰富

**负面**:
- 性能略低于 gRPC
- 类型安全性较弱
